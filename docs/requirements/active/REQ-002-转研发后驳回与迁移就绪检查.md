## 一、需求描述

### 1.1 背景

GPCM 接入灵问作为反馈入口（GPCM REQ-049）。两处缺口：

1. 工单转研发（已建 Gitea Issue）之后，后台人员发现不该做（重复、不在支持范围、提交有误），只能去 Gitea 手动关 Issue；灵问会把这次关闭当成“关闭未修复”（`closed`），驳回原因无处记录，提交人收不到说明。现有 `reject` 只能处理待确认工单。
2. GPCM 主库在灵问迁移尚未执行（缺表）时不应整站报错，只应禁用反馈入口；需要一个不改库的检查手段，并能区分“未就绪”与“查询失败”。

### 1.2 目标

- 有管理权限的人（接入方映射为 `reviewer` / `admin`）可驳回已转研发的工单：工单、评论、历史全部保留，只关闭工单明确关联的主 Issue；关闭异步、持久化、可重试、防重复，失败可查、可手动重试；之后 Gitea 回流不覆盖本地驳回结论。
- 提供只读的迁移状态检查函数，供接入方按结果降级。

### 1.3 范围与边界

- **本期包含**：驳回已转研发工单（Go / REST / MCP）、关闭 Issue 任务的进度查询与重试、Webhook 与对账对驳回工单的保护、迁移状态检查 `lingo.CheckMigrations`、确认并补测“后台人员随时评论”的已有契约。
- **本期不包含**：无 Gitea 模式（Gitea 配置仍必填）；驳回时在 Issue 上评论、改标签或处理 PR；撤销驳回；通用的 outbox 任务管理接口；迁移检查的 REST 接口（接入方在 `New` 之前就要用，以 Go 函数提供）。

## 二、功能需求

### 2.1 驳回已转研发工单

- **可驳回的状态**：`submitted`、`open`、`in_progress`、`need_info`、`abnormal`（仅限没有修复记录的：建单失败，或处理中的工单 Issue 被删除 / 读取 404；已记录修复 PR / 提交 / 版本 / 上线的 `abnormal` 返回 `conflict`。已关闭（未修复）工单的 Issue 被删除或读取 404 时保持 `closed`、不转 `abnormal`，因此仍不可驳回。早期版本已由 `closed` 转为 `abnormal` 的存量工单，在工单行锁内读取与状态变更同事务写入的状态历史：最近一条进入 `abnormal` 的记录（`status=abnormal` 且 `prev_status` 不是 `abnormal`；建单失败 `issue.create_failed` 视为从 `submitted` 进入）的 `prev_status` 为 `closed` 时返回 `conflict`，无需迁移）；`fixed` / `released` / `deployed`（已有修复）与 `closed`、`answered`、`merged` 返回 `conflict`；`pending_triage` 返回 `conflict`，仍用原有 `reject`。
- **权限**：`reviewer` / `admin`，且工单在其 `User.Projects` 内（项目外返回 `not_found`）；`external` / `agent` 返回 `forbidden`。
- **原因**：`reason` 必填（去首尾空白后非空），作为 `ticket.status` 事件正文对提交人可见，并写入审计 `ticket.rejected`（含操作人、原状态、关联 Issue）。
- **结果**：状态改为 `rejected`；工单、评论、附件、历史不删除；`issue_url` 仍返回。发出 `ticket.status`（`prev_status` 为原状态），不发 `triage.resolved`。
- **关闭 Issue**：工单已关联主 Issue 时，同一事务内入队 `close_issue`（outbox，幂等键 `close_issue:ticket:<id>`）；worker 读取 Issue，已关闭视为完成，否则 `PATCH state=closed`。读取或关闭返回 404 时不按完成处理：Gitea 对 Issue 已删除、机器人无权查看仓库、Issues 被禁用或单独拒权都返回 404，仓库可读也不能证明已删除，任务直接置为 `failed`，`last_error` 写明原因，可人工重试（本期不做删除的正向识别）。只关闭库中记录的工单仓库 + 主 Issue 编号，不按标记搜索、不改标签、不动 PR 与其他 Issue。
- **驳回原因评论**（待办 #698）：关闭前机器人在该 Issue 上留一条原因评论。原因与驳回人姓名取自审计 `ticket.rejected`（`note` / `rejected_by`），重试轮次与建单途中驳回后补记 Issue 时沿用原原因与署名。评论只署后台人员姓名快照（`User.Name`；为空时不署名，不以用户 ID 代替），不写提交人姓名、邮箱、用户 ID；原因中的灵问标记会被去掉。评论末尾带隐藏标记 `<!-- lingo:reject=<工单ID> -->`，已有机器人发出的同一标记评论时不再发，重试与重复执行只留一条。Issue 已关闭时只补评论。早期版本入队、载荷没有原因的任务只关闭不评论。列出评论或发评论返回 404 时同关闭的 404 处理。
- **失败原因脱敏**（待办 #698）：`close_issue` 写入 outbox `last_error`（经 `IssueClose.LastError` 给 reviewer / admin 查看）的只有脱敏说明：类别与 HTTP 状态码，如“机器人账号无权评论或关闭该 Issue（HTTP 403）”“Issue 不存在或机器人无权访问（HTTP 404），无法确认已关闭”。不含地址、令牌、响应正文，原始错误只记日志。
- **重试与失败**：5xx / 429 / 网络错误按 outbox 通用退避（10 秒起翻倍，最长 1 小时）重试，失败 10 次或遇到 403、无法确认删除的 404 等不可重试错误后任务置为 `failed` 并保留原因；工单保持 `rejected`，不会变为 `abnormal`。
- **幂等与并发**：对已驳回工单重复调用返回当前工单，不重复留痕、通知或入队；并发调用经工单行锁串行，只生效一次。
- **建单途中驳回**：`submitted` 尚无 Issue 时只改状态；建单任务随后跳过。若 Gitea 已建好 Issue 而结果尚未记下（建单与驳回并发，或进程在建单后崩溃），建单结果回写、重试查重或 Webhook 按标记补记时关联该 Issue 并入队关闭，工单保持 `rejected`。
- **驳回前已排队的同步**：驳回前已入队、尚未执行的补充评论（`create_comment`）、标签移除（`remove_label`）与视角同步（`sync_perspectives`）在驳回后直接完成、不写 Gitea，内容留在灵问。补充评论被拦下时置 `lingo_ticket_comments.withheld_at`，并记审计 `comment.withheld`（`source=system`，payload 含 `comment`、`issue`、`repo`，不发事件，同一条只记一次）；
- **补充评论外发与驳回的仲裁**（待办 #698）：判定不以 worker 的无锁状态读取为准，二者都在工单行锁（`SELECT … FOR UPDATE`）下的短事务中判定。
  - worker 发补充评论（含其附件上传、改评论）前先取得发送租约：`lingo_ticket_comments.sending_until = 数据库 now() + 本次任务剩余时限 + 10 秒`。驳回先提交时取不到租约，一个请求也不发（见上一条）。
  - 租约先提交时，`RejectForwarded` 在同一把锁下看到有效租约就不提交：在事务外每 100 毫秒重试，最多等 5 秒；仍在发送则返回 `conflict`（409，工单不变，稍后重试）。
  - 本次发送结束即释放租约，驳回随后提交。任务内的全部 Gitea 请求共用同一个带截止时间的 ctx，租约过期时本次发送必然已经结束；进程崩溃时租约到期自然失效。
  - HTTP 请求在事务之外发出，不持有数据库连接与行锁。已经发出的请求不追撤。
  - 关单链路（`close_issue`）不经过租约；已驳回工单的重复驳回（幂等返回）也不受影响。
  - 判定点：worker 在锁内读到驳回前取得的租约才算“已发出”；驳回在租约之后提交的，这条评论照常发出。建单与驳回并发时，Issue 建好后不再补传附件、不改正文。
- **回流保护**：工单为 `rejected` 后，Gitea 的 `issues` 关闭（含灵问自己关闭的回声）/ 重开 / 删除、指派、标签、里程碑、对账快照与 PR 合并都只记审计，不改状态、排期与修复记录，不发状态事件；研发重开 Issue 也不会被再次关闭。

### 2.2 关闭进度查询与重试

- 进度：`state` 取 `none`（没有要关闭的 Issue）/ `pending` / `done`（已关闭或本就关闭）/ `failed`（含 Issue 返回 404），附轮次 `attempt`、本轮失败次数、最近失败原因与更新时间；只读。
- 重试：仅 `failed` 时入队新一轮（幂等键 `close_issue:ticket:<id>:retry:<n>`）并记审计 `issue.close_retry`；`pending` / `done` 时直接返回当前进度，不重复入队；没有可关闭的 Issue 返回 `conflict`。权限同驳回。

### 2.3 后台人员随时评论（已有契约，本期补测试）

`reviewer` / `admin` 可在任何状态写对外评论（`source=staff`），不改变工单状态；工单已转出且有 Issue（非 `abnormal`）时由机器人同步为 Issue 评论，未转出或已驳回的只留在灵问。例外：`merged` 工单返回 `conflict`（评论应写到合并目标）。

### 2.4 迁移状态检查

- `lingo.CheckMigrations(ctx, db)`：在只读事务中对比本版本内嵌迁移与 `db` 当前 schema（`search_path` 第一项，与 `Migrate` 一致）；不建表、不补列、不回填校验和、不取 advisory lock、不写入。查询会取普通读锁（AccessShareLock），遇到持有排他锁的 DDL（如 `Migrate` 进行中）会等待，调用方应给 ctx 设置超时。缺表按迁移 SQL 中的 `CREATE TABLE` / `DROP TABLE` 推算（忽略注释），迁移的表名写法须满足 PRD 5.4 的约束。
- 结果 `MigrationStatus`：`ready`、`applied`、`pending`（未执行）、`changed`（已执行但内容不同）、`unknown`（库中有、本版本没有，即库已由更新版本迁移，不影响就绪）、`missing_tables`（已执行迁移应建而不存在的表；迁移记录表不存在时为 `lingo_schema_migrations`）。`ready = pending、changed、missing_tables 均为空`。
- 错误：`err == nil` 时看 `Ready`（未就绪不是错误）；`err != nil` 表示检查本身失败（连接、超时、权限、ctx 取消），状态未知，调用方应重试或告警，不应据此执行迁移。

## 三、接口

| Go | REST | MCP | 说明 |
|----|------|-----|------|
| `l.RejectForwardedTicket(ctx, u, id, reason)` → `Ticket` | `POST /tickets/{id}/reject-forwarded` `{"reason":"…"}` → 200 | `reject_forwarded_ticket {id, reason}` | 驳回已转研发工单 |
| `l.TicketIssueClose(ctx, u, id)` → `IssueClose` | `GET /tickets/{id}/issue-close` → 200 | `get_issue_close {id}` | 关闭进度 |
| `l.RetryTicketIssueClose(ctx, u, id)` → `IssueClose` | `POST /tickets/{id}/issue-close/retry` → 200 | `retry_issue_close {id}` | 失败后重试 |
| `lingo.CheckMigrations(ctx, db)` → `MigrationStatus` | - | - | 只读迁移检查 |

`IssueClose` JSON：`{"ticket_id","repo","issue","state","attempt","failures","last_error","updated_at"}`（`repo` / `issue` / `last_error` / `updated_at` 为空时省略）。

错误码：`invalid_input`（400，原因为空）、`forbidden`（403，非 reviewer / admin）、`not_found`（404，不存在或项目外）、`conflict`（409，状态不可驳回 / 无 Issue 可重试 / 有补充评论正在发往 Gitea，等待 5 秒后仍未结束）。

## 四、数据与兼容

- 复用 `lingo_outbox`（`key` 唯一索引）、`lingo_ticket_events`、`lingo_events`；`rejected` 已在状态约束中。
- 迁移 `0002_comment_send_lease.sql`（待办 #698）：`lingo_ticket_comments` 增加 `sending_until`（发送租约）、`withheld_at`（驳回后未发出），均可空、向前兼容。宿主需执行 `lingo.Migrate`；未执行时 `CheckMigrations` 报 `pending`。
- 公开 API 只增不改（新增方法、类型、REST 路径与 MCP 工具），属 minor 版本；`RejectTicket` 行为不变。
- `rejected` 的含义扩展为“待确认时驳回，或转研发后驳回”；后者带 `issue_url`。`agent` 对 `rejected` 工单仍不可见（同既有规则）。

## 五、验收标准

- [x] 已转研发工单驳回后状态为 `rejected`，评论与历史保留，提交人收到带原因的 `ticket.status`
- [x] 关联主 Issue 被关闭一次；并发 / 重复驳回只入队一次
- [x] 关闭遇不可重试错误后进度为 `failed` 且带原因；修复后重试完成，重复重试不重复入队
- [x] 驳回后 Gitea 关闭回声、重开、删除不改变工单状态，也不再次关闭
- [x] reviewer / admin 在各状态都能评论（merged 除外），驳回后的评论不发往 Issue
- [x] 关闭前在该 Issue 上留一条驳回原因评论（只署后台人员姓名、不含提交人信息，去重只留一条；重试沿用原原因）；关闭失败原因脱敏
- [x] 补充评论外发与驳回由工单锁下的发送租约仲裁：驳回先提交则评论及附件请求不发并记 `comment.withheld`；发送先取得租约则驳回在其结束前不提交（最多等 5 秒，之后 409）；已发出的不追撤
- [x] 空库、缺表、迁移被改、缺迁移记录分别得到未就绪结果，检查不建表、不改数据；连接不可用 / ctx 取消返回错误
