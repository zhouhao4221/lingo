## 一、需求描述

### 1.1 背景

GPCM 配置 `GiteaConfig.ReplyMode = ReplyAll`：Gitea 上全部非机器人评论都对提交人可见（`public`）。升级前，交给模型的工单评论直接取
`public`：普通用户（external）问答带对外评论、结案工单自动抽取知识用对外评论。于是 ReplyAll 下研发内部讨论也会进入模型输入，并经
抽取的知识、被标为“有帮助”的回答、向量与会话历史间接扩散到其他用户的问答中。

用户可见范围（ReplyAll）是 GPCM 已确认的业务口径，不改；本需求把“能否交给模型”与“用户是否可见”分开：新增显式启用的模型内容策略，
启用后模型只接收 ReplyMarked 旧内容范围内、来源可信的内容。

### 1.2 范围与边界

- **本期包含**：`Config.ModelContent`（`ModelContentMarked`）；评论、助手消息、派生知识的来源记录（迁移 0009）；问答、知识检索、
  向量、历史、自动抽取、回答候选的统一过滤；按新规则手动重新抽取 `ReextractTicketKnowledge` / `POST /tickets/{id}/knowledge/reextract`；
  `KnowledgeEntry.ModelInput`；单测、集成测试、文档
- **本期不做**：
  - 修改 ReplyMode 语义、用户可见范围、同事 / 合并工单 / 项目 / 管理权限与通知机制
  - 删除或改写任何已有记录（评论、知识、审核状态、会话消息、已有向量）
  - 自动重新抽取、批量重新抽取、人工豁免或“信任未知”的开关
  - MCP 工具（重新抽取只由 GPCM 后台手动调用）
  - 改变未启用新策略的接入方的既有行为

## 三、业务规则

### 3.1 模型准入（启用 `ModelContentMarked` 时）

| 内容 | 准入（可作为模型输入） | 不准入 |
|------|------|------|
| Gitea 评论 | 同步时原始正文以 `/reply` 开头或含 `<!-- lingo:public -->`（与 ReplyMode 无关），且判定与当前版本一致 | 普通评论；升级前同步、尚未重新判定的（`model_marked` 为 NULL，来源未知）；判定后被旧版本改写过正文的（版本不一致） |
| 灵工本地评论 | 提交人补充、后台答复、MCP 回复（显式对外） | 其他来源 |
| 知识条目 | 人工在灵工中填写：`manual`、`ticket_answer`、`ticket_comment`；派生条目 `model_ok = true` | 升级前的派生条目（`ticket_extract`、`assistant_feedback`，NULL）；`model_ok = false` |
| 会话历史 | 用户自己的提问；`marked` 的回答；当前为 reviewer / admin / agent 时 `authorized` 的回答（只因该角色已授权的评论范围） | 未知的回答（升级前、失败、被旧版本改写过内容，所有角色）；`untrusted` 的回答（所有角色）；external 会话中 `authorized` 的回答 |

- 不准入的历史回答用“（此条回答已省略）”占位，引用的工单与版本照常保留（指代与留言目标用）；消息本身不改
- 判定只依据可信的原始标记或可靠元数据（来源字段、生成时记录且与版本一致的 `model_marked` / `model_scope`、派生条目的 `model_ok`）；不以现有 `public`、当前快照、时间、当前权限、当前评论状态或
  “缺乏记录”推断历史内容安全

### 3.2 各模型消费功能

| 功能 | 启用后 | 未启用（默认） |
|------|------|------|
| external 工单问答（单张工单最近 5 条评论） | 只取 `Comment.Model` 的评论 | 对外评论（不变） |
| reviewer / admin / agent 工单问答 | 不变（含内部讨论，已授权范围） | 不变 |
| 知识问答检索 | 只含 `ModelInput` 条目（所有角色） | 不变 |
| 知识向量生成 | 只为 `ModelInput` 条目生成；其他条目已有向量保留 | 不变 |
| 结案工单自动抽取 | 只用 `Comment.Model` 评论，候选 `model_ok = true` | 对外评论（不变），候选如实记录 `model_ok` |
| 回答“有帮助”候选 | 候选 `model_ok` = `ScopeTrusted(回答的 model_scope)`：只有 `marked` 为 true，`authorized` / `untrusted` 为 false，未知为 NULL | 同左（只记录，不影响行为） |
| 意图解析、确认判断 | 历史同上过滤 | 不变 |
| 用户检索 `SearchKnowledge` | 不变（照常展示全部；不返回 `model_input`） | 不变 |
| 维护列表、审核 | 不变（照常展示全部），另返回 `model_input` | 同左 |

### 3.2.1 助手消息的内容范围（model_scope）

| 值 | 含义 | 回放（启用后） | 回答候选 |
|----|------|------|------|
| `marked` | 送给模型的评论都在 ReplyMarked 范围内，知识条目与历史回答都来源可信 | 所有角色 | 可信（`model_ok = true`） |
| `authorized` | 另含提问人角色已授权、不在 ReplyMarked 范围内的评论（reviewer / admin / agent 看到的内部评论，或回放了 `authorized` 的历史），没有其他不可信内容 | 只对当前为 reviewer / admin / agent 的会话所有者 | 不可信（`false`） |
| `untrusted` | 含来源未知或不可信的知识条目、未知或不可信的历史回答，或 external 问答中不在范围内的评论（未启用策略时） | 不回放（所有角色） | 不可信（`false`） |
| NULL（未知） | 升级前的消息、失败的回答、用户消息，或写入后被旧版本改写过内容 | 不回放（所有角色） | 未知（NULL） |

- 一轮的范围取本轮实际送给模型的内容中最不可信的一档；不回放的历史以“（此条回答已省略）”占位，引用的知识条目也不交给模型
- 未启用策略时历史照常回放（行为不变），回放了 `untrusted` / 未知回答的新回答如实记为 `untrusted`
- “同类角色”按当前角色判断（会话只有所有者可访问；引用的工单另按当前可读范围重新判断，见 REQ-004）

### 3.3 来源链（新记录）

| 记录 | 写入 | 规则 |
|------|------|------|
| Gitea 评论 `model_marked` | 创建、编辑（Webhook / 对账 / 重新同步） | 乱序旧版本、已删除的不覆盖；只有判定变化时同样写入，但不留痕、不改可见性计数、不通知（Resync 计为 Unchanged）；同时写入 `model_marked_at` = updated_at、`model_marked_md5` = md5(body) |
| 助手消息 `model_scope` | 每次回答（含重试） | 见 3.2.1；失败的回答为 NULL；无论是否启用都记录；同时写入 `model_scope_at` = updated_at、`model_scope_md5` = md5(content) |
| 派生知识 `model_ok` | 自动抽取、重新抽取、回答候选 | 抽取：送给模型的评论都准入时为 true；候选：回答为 `marked` 时 true、`authorized` / `untrusted` 时 false、未知时 NULL |

**版本绑定（评审 B1）**：评论与助手消息的判定只对写入时的那个版本有效。读取时 `*_at = updated_at` 且 `*_md5 = md5(正文)` 才采用判定，
否则按未知处理。旧版本实例（滚动升级期间，或回退到 v0.11.0 后再升级）改写正文时不会更新这些列，旧判定随之失效；新版本再次同步或回答时重新判定。
知识条目的 `model_ok` 不绑定版本：它描述条目的来源；旧版本对已有条目的改写只有人工编辑与审核（新版本对人工编辑同样保留来源判定），
不会把派生内容写进已有条目（派生条目只新增，冲突时不写）。

### 3.4 重新抽取（方案 A）

| 类型 | 规则 |
|------|------|
| 权限 | 仅 reviewer / admin（先于查找，external / agent 403）；工单须在 `User.Projects` 内，否则与不存在一样 404 |
| 适用 | 该工单已有来源未知或不可信的抽取条目，且仍为已结案（released / deployed / closed）的 Bug / 需求工单；否则 409 |
| 输入 | 只用 `Comment.Model` 的评论（同启用后的规则，不看是否启用）；返回送给模型的评论数与被排除的对外评论数 |
| 结果 | 新候选 `ticket_extract`、待审核、`model_ok = true`，走正常审核；旧条目内容、状态、审核结果不改 |
| 幂等 | 已有来源可信的抽取条目时返回它（`exists`），不调用模型；模型认为无可复用知识时 `skipped`、不入库 |
| 触发 | 只由调用方手动触发；不自动重新抽取；不提供人工豁免 |
| 并发 | 与自动抽取共用 `lingo_knowledge_extractions` 的租约（`locked_until`），同一工单串行：后到的等待先到的完成（最多 60 秒，超时 409）后重新判断，返回 `exists`，不重复调用模型；工单没有抽取登记时登记为已完成。自动抽取失败后处于重试延迟内（`locked_until` 为未来时间）时，重新抽取同样等待，最多 60 秒后返回 409（稍后重试）——预期行为 |
| 自动抽取 | 每张工单只自动抽取一次（与 v0.11.0 契约一致：原唯一索引本就不允许第二条抽取候选，原先是调用模型后入库冲突再记完成，现在调用前判断，结果相同、少一次模型调用）：工单已有任何抽取条目（含重新抽取的）时不调用模型、直接记为完成（评审 N2：避免“入库成功、记完成失败”重试后出现不可信与可信各一条） |
| 模型 | 无抽取模型（LightModel / Model）时 `ErrNoModel`（REST 501）；每次调用（exists 除外）调用一次抽取模型并计用量 |
| 前置 | 升级前同步的 Gitea 评论来源未知、不会交给模型；需要时先 `ResyncTicketComments`（GPCM 用 `Notify=false`） |

### 3.5 不变的部分

- ReplyMode 继续决定用户可见范围（GPCM ReplyAll：全部非机器人评论）；`ResyncTicketComments` 契约（计数、`Notify`、审计、幂等）不变
- 同事（`TicketAudience`）、合并工单、项目范围、管理权限、通知（Notifier / 变更流）规则不变
- 未启用新策略的接入方：交给模型的内容与升级前一致，只额外记录来源列

## 四、接口契约

### 4.1 Go

- `type ModelContentPolicy string`；`ModelContentDefault = ""`、`ModelContentMarked = "marked"`
- `Config.ModelContent ModelContentPolicy`
- `KnowledgeEntry.ModelInput *bool`（JSON `model_input`，只在维护接口返回；普通用户检索结果中省略——是否作为模型输入是维护信息，对检索的用户没有用处，评审 N1）
- `func (l *Lingo) ReextractTicketKnowledge(ctx context.Context, u User, ticketID int64) (KnowledgeReextract, error)`
- `KnowledgeReextract{TicketID int64; Outcome string; Entry *KnowledgeEntry; Comments, Excluded int}`
  - JSON：`ticket_id`、`outcome`（`created` | `exists` | `skipped`）、`entry`（可省略）、`comments`、`excluded`
  - 常量：`KnowledgeReextractCreated`、`KnowledgeReextractExists`、`KnowledgeReextractSkipped`

GPCM 启用示例：

```go
lingo.Config{
	ModelContent: lingo.ModelContentMarked,
	Gitea:        lingo.GiteaConfig{ReplyMode: lingo.ReplyAll /* … */},
	// …
}
```

### 4.2 REST

`POST /tickets/{id}/knowledge/reextract`（无 body）

- 200：`KnowledgeReextract` JSON
- 401 未认证；403 `forbidden`（非 reviewer / admin）；404 `not_found`（不存在或不在项目范围）；409 `conflict`（没有来源未知的抽取条目、
  工单未结案或不是 Bug / 需求）；501 `model_not_configured`（无抽取模型）

### 4.3 数据库（迁移 0009）

| 表 | 列 / 索引 | 说明 |
|----|------|------|
| `lingo_ticket_comments` | `model_marked boolean`、`model_marked_at timestamptz`、`model_marked_md5 text` | 只对 `source = 'gitea'` 有意义；NULL = 升级前同步；与版本绑定 |
| `lingo_assistant_messages` | `model_scope text`（marked / authorized / untrusted）、`model_scope_at timestamptz`、`model_scope_md5 text` | NULL = 升级前 / 失败 / 用户消息；与版本绑定 |
| `lingo_knowledge` | `model_ok boolean` | 只对派生来源有意义；NULL = 升级前 |
| `lingo_knowledge` | `lingo_knowledge_extract_ticket_idx`（重建，`model_ok IS NOT TRUE`）、`lingo_knowledge_extract_trusted_idx`（新，`model_ok`） | 每张工单来源未知 / 不可信与可信的抽取候选各最多一条 |

## 五、兼容性与风险

- **公开 API 只增不改**：新增类型、常量、字段与方法；`KnowledgeEntry` 新增 `model_input` 字段（只在维护接口返回，JSON 多一个键）
- **迁移锁表**：0009 以非 CONCURRENTLY 方式重建 `lingo_knowledge` 的部分唯一索引，执行期间短暂阻塞该表写入（表通常很小），请在发布窗口执行
- **迁移向前兼容**：只加可空列、不改写已有行；旧版本（v0.11.0）写入时新列为 NULL（视为未知，启用后不准入），抽取候选仍受“每张工单一条”约束
  （重建的索引覆盖 NULL）；与旧版本同时运行时，旧版本仍按旧规则把内容交给模型——启用新策略前应先完成所有实例升级
- **回退**：v0.11.0 不认识新策略，回退后按旧规则把对外评论（ReplyAll 下为全部非机器人评论）、来源未知的知识与历史回答交给模型。回退不得扩大
  模型输入：先停止调用重新抽取接口；先恢复原 ReplyMarked 配置并完成必要的安全核对，无法确认时停用相关的模型消费（代码配置中以拒绝调用的模型
  代替 Model / LightModel）直至重新升级并启用策略；接受扩大外发不是默认回退方式。保留 0009 及历史数据，不做 down、不删改记录。回退期间写入的
  记录重新启用后一律按来源未知处理。详见 v0.12.0 版本说明“回退到 v0.11.0”
- **启用后的可感知变化（仅 GPCM）**：升级前同步的 Gitea 评论在重新同步前不交给模型，问答内容可能变少；升级前的派生知识与历史回答不再
  进入问答；这些是有意的保守处理
- **人工条目可信**：`manual` / `ticket_answer` / `ticket_comment` 视为可信来源（人工在灵工中填写并显式入库）；人工审核通过、编辑来源未知的
  派生条目不改变其来源判定（不提供豁免）
