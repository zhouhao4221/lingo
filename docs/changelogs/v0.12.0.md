# v0.12.0（2026-11-27）

模型内容策略（防御性数据最小化，REQ-012，待办 #793）：
- 新增显式启用的 `Config.ModelContent = lingo.ModelContentMarked`：模型准入与用户可见（`ReplyMode`）分开，external 问答与结案工单自动抽取只把
  ReplyMarked 范围内的评论交给模型；问答检索、知识向量、会话历史与回答候选只用来源可信的内容
- 新增 `ReextractTicketKnowledge` 与 REST `POST /tickets/{id}/knowledge/reextract`，手动按新规则为来源未知的旧抽取知识重新抽取待审核候选

公开 API 只增不改；**数据库迁移 0009**（只加可空列、拆分抽取候选唯一索引，不改写已有行）；默认不启用，既有行为不变。

要求：同 v0.11.0（Go 1.24+、PostgreSQL 13+、Gitea 1.22+）。

## 新功能 (Features)

- **模型内容策略**（REQ-012）
  - **Go**：`type ModelContentPolicy string`（`ModelContentDefault = ""`、`ModelContentMarked = "marked"`）；`Config.ModelContent`；其他取值 `New` 报错。
  - **启用后**：
    - Gitea 评论按同步时原始正文的 `/reply` / `<!-- lingo:public -->` 标记判定是否准入（与 ReplyMode 无关），Webhook、定时对账、`ResyncTicketComments`
      一致；乱序旧版本与已删除的不覆盖；升级前同步、尚未重新判定的不准入。灵工本地的提交人补充、后台答复、MCP 回复照常准入。
    - external 工单问答只带准入的评论；reviewer / admin / agent 的已授权范围不变。
    - 知识问答检索与向量生成只用 `KnowledgeEntry.ModelInput` 的条目（人工填写的 manual / ticket_answer / ticket_comment，或按可信内容生成的派生条目）；
      其他条目照常展示、审核、维护，已有向量保留。
    - 会话历史按助手消息的三档内容范围回放：`marked` 对所有角色回放；`authorized`（只因已授权的内部评论）只对 reviewer / admin / agent
      回放；`untrusted` 与未知（升级前、失败或被旧版本改写过的回答）对所有角色都不回放，以“（此条回答已省略）”占位，引用的知识也不交给模型
      （引用的工单与版本保留）。
    - 自动抽取只用准入的评论；回答“有帮助”候选只有回答为 `marked` 时可信（`authorized` / `untrusted` 为不可信，未知为来源未知）。
  - **未启用**：交给模型的内容与 v0.11.0 相同，只额外记录来源（新列）。
  - **`KnowledgeEntry.ModelInput *bool`**（JSON `model_input`）：只在维护接口返回。
  - 评论与助手消息的判定与写入时的版本绑定（updated_at + 正文 md5），被旧版本改写过的按未知处理；助手消息记录三档内容范围
    `marked` / `authorized`（reviewer / admin / agent 已授权的内部评论，只对这些角色回放）/ `untrusted`（不回放）。

- **按新规则重新抽取**（REQ-012 方案 A）
  - **Go**：`func (l *Lingo) ReextractTicketKnowledge(ctx context.Context, u User, ticketID int64) (KnowledgeReextract, error)`；
    `KnowledgeReextract{TicketID, Outcome, Entry, Comments, Excluded}`，`Outcome` 为 `KnowledgeReextractCreated` | `Exists` | `Skipped`。
  - **REST**：`POST /tickets/{id}/knowledge/reextract` → 200 / 401 / 403 / 404 / 409 / 501。
  - 仅 reviewer / admin、限 `User.Projects`；只适用于已结案的 Bug / 需求且已有来源未知或不可信的抽取条目；旧条目不改；新候选待审核；
    已有可信候选时返回它且不调用模型；只手动触发；与自动抽取共用租约，同一工单并发时后到的等待后返回 exists。
  - 自动抽取遇到已有任何抽取条目的工单不再调用模型（每张工单只自动抽取一次）。

## 行为变化

**未启用策略（默认 `ModelContentDefault`）**
- 交给模型的内容与 v0.11.0 逐字一致：问答的评论、知识检索结果、会话历史、送给向量模型的文本、自动抽取的输入都不变（集成测试逐字比对）。
- 新列照常写入（评论的模型判定、助手消息的内容范围、派生知识的来源），只记录，不影响行为。
- 自动抽取遇到**已有抽取条目**的工单时不再调用模型，直接记为完成。结果与 v0.11.0 相同：v0.11.0 的唯一索引本就不允许同一工单出现第二条抽取候选，
  旧代码是调用模型后在入库时冲突再记完成；现在只是少一次无效的模型调用与用量记录（`GET /usage` 中 `knowledge_extract` 次数随之减少）。
  这种情况只出现在“入库成功、记完成失败”后的重试，或调用了新的重新抽取接口之后。
- 维护接口（`ListKnowledge`、审核等）返回的 `KnowledgeEntry` 多一个 `model_input` 字段；普通用户检索结果不变。新增 REST 路由
  `POST /tickets/{id}/knowledge/reextract`；其他接口与 MCP 工具不变。

**启用 `ModelContentMarked` 后（实际可感知的变化）**
- 升级前同步的 Gitea 评论在重新判定前不交给模型：external 问答中工单评论会变少，直到逐张 `ResyncTicketComments`（或该评论被编辑）。
- 升级前生成的抽取知识与回答候选（来源未知）不再进入问答检索，也不再生成向量；照常展示、审核、维护，内容与审核状态不改。
- 升级前的历史回答在后续提问中以“（此条回答已省略）”占位，多轮对话的上下文变短；reviewer / admin / agent 会话中只因内部评论的回答照常回放。
- 用户可见范围（ReplyMode）、同事、合并工单、项目与管理权限、通知、`ResyncTicketComments` 的契约都不变。

## 回退到 v0.11.0

v0.11.0 不认识 `ModelContent`：回退后它按旧规则把对外评论（ReplyAll 下即全部非机器人评论）、来源未知的知识与历史回答交给模型。
**回退不能以扩大模型输入为代价，接受扩大外发不是默认的回退方式。** 回退前按顺序：

1. **先停止调用新的重新抽取接口**（`ReextractTicketKnowledge` / `POST /tickets/{id}/knowledge/reextract`；v0.11.0 没有该方法与路由）。
2. **先保证回退后不会扩大模型输入**，二选一：
   - **恢复保护后再回退**：把 `GiteaConfig.ReplyMode` 恢复为原来的 `ReplyMarked`，并完成必要的安全核对后再切换版本。注意 v0.11.0 只看库中已保存的
     `public`：ReplyAll 期间已保存为对外的普通评论仍是对外，来源未知的派生知识与历史回答仍会交给模型。核对不了、或处理这些数据需要改变用户可见范围
     或知识状态（属于业务决定，需另行确认）时，不要走这条路。
   - **停用相关的模型消费直至恢复保护**（无法确认时的默认做法）：在 v0.11.0 的代码配置中把 `Config.Model` 与 `Config.LightModel` 设为一个拒绝调用的
     模型（每次 `Chat` / `Embed` 都返回错误；代码配置优先于数据库中的连接配置，不要依赖清空数据库配置）。效果：知识问答失败（可重试）、不生成向量、建单整理退回原内容
     （不影响建单）；自动抽取按失败退避，同一工单连续失败 3 次后记为失败、之后不再自动抽取（需要时恢复保护后手动重新抽取）。保持停用，直到重新升级到 v0.12.0 并启用 `ModelContentMarked`。
3. 滚动回退期间新旧实例并存时同样适用：先让将要运行 v0.11.0 的实例按第 2 步处理，再切换版本。
4. **保留 0009 及历史数据，不做 down**：v0.11.0 不读写新列（`CheckMigrations` 会把 0009 列入 `Unknown`，不影响 `Ready`）；不删除、不改写评论、知识、
   审核状态与会话消息。回退期间不调用任何真实服务做验证。

**重新升级 / 重新启用的风险（旧历史保守处理）**
- 回退期间由 v0.11.0 写入或改写的评论、助手消息、派生知识，新列为空或与版本不一致，重新启用后一律按来源未知处理：评论需重新同步后才准入，
  那段时间的回答不回放，那段时间生成的抽取知识与回答候选不进入问答（需要时手动重新抽取）。不会因时间、当前权限或当前评论状态被推断为可信。
- 回退期间 v0.11.0 的自动抽取不认识可信候选：已手动重新抽取过、但抽取登记仍为待处理的工单，可能再多一条来源未知的候选（两条都保留，照常审核；
  来源未知的那条启用后不进入问答）。
- 重新启用前同样要求全部实例为 v0.12.0。

## 已知限制

- **锁表**：0009 以非 CONCURRENTLY 方式重建唯一索引，执行期间短暂阻塞 `lingo_knowledge` 的写入（表通常很小），请在发布窗口执行。
- **重新抽取的 60 秒等待**：同一工单上的重新抽取与自动抽取共用租约；同时调用时后到的最多等待 60 秒，超时返回 409（稍后重试）。自动抽取失败后处于
  重试延迟内（租约到期时间在未来）时，重新抽取同样等待并可能返回 409，属于预期行为。
- **多实例**：策略按实例配置，必须全部实例为 v0.12.0 且配置一致才完整生效；与 v0.11.0 混跑期间旧实例按旧规则把内容交给模型。
- **旧版不认新策略**：v0.11.0 及更早版本不读 `ModelContent` 与新列（回退要求见上）。
- 升级前同步的评论需逐张 `ResyncTicketComments` 才能重新判定；重新抽取逐张手动调用，无批量与 MCP 工具，每次调用计模型用量。
- 人工在灵工中填写的知识（`manual` / `ticket_answer` / `ticket_comment`）视为可信来源；审核通过或编辑来源未知的派生条目不改变其来源判定（不提供豁免）。
- 只在隔离测试中验证（合成数据、假模型、只读假 Gitea、临时 PostgreSQL）；GPCM 联调尚未进行。
