# v0.10.0（2026-11-26）

知识问答图片提问：提问可以附带最多 4 张图片引用，灵工经 `Config.FetchAttachment` 以提问人身份读取、按内容校验后，发给**声明支持图片**的模型。公开 API 只增不改；新增迁移 `0008_assistant_attachments.sql`，升级后需执行 `lingo.Migrate`。**图片能力默认关闭**，不声明时行为与 v0.9.0 相同。

要求：Go 1.24+、PostgreSQL 13+、Gitea 1.22+（同 v0.9.0）。不需要数据库扩展。

> ⚠️ **启用前门禁**：在明确真实业务图的外发范围与模型服务商授权之前，任何环境都不要声明 `images`（`OpenAIConfig.Images`、连接配置 `model.*.images`、自定义模型的 `ImageModel`）。

## 新功能 (Features)

- **知识问答图片提问**（#53，REQ-009）
  - **入参**：`MessageInput.Attachments []Attachment`（只取 `ID`、`Name`、`ContentType`、`Size`，带 `URL` 返回 `ErrInvalidInput`）；有图时 `Content` 可以为空。REST `POST /conversations/{id}/messages` 新增 `attachments`；MCP `ask` 新增 `attachments`，有图时 `question` 可不填。
  - **限制**：每条最多 `MaxQuestionImages` = 4 张；单张按实际读取不超过 `MaxQuestionImageBytes` = 5 MB（合计约 20 MB，无单独总量上限）；宽高各 1–`MaxQuestionImageSide` = 8192 像素（无单独总像素上限）；只收 PNG、JPEG（含 image/jpg）、WebP，按文件头识别且须与声明一致；单张读取 30 秒时限。
  - **读图回调**：`FetchAttachment` 收到的 `Attachment` 新增 `Purpose`（`AttachmentForTicket` / `AttachmentForQuestion`）、`TicketID`、`ConversationID`、`MessageID`（均 `json:"-"`）。提问图片的 `userID` 为提问人；接入方须核对该图由此人上传、且允许外发，拒绝时返回 `ErrNotFound` / `ErrForbidden`。工单附件的调用另带 `Purpose=ticket` 与 `TicketID`，其余不变，原有授权不放宽。
  - **模型能力**：新增 `ImageModel`、`Message.Images` / `Image`、`OpenAIConfig.Images`、`ModelSlotSettings.Images` / `ModelSlotUpdate.Images`（只能用于 openai 类型；DeepSeek 不支持）。按 OpenAI 兼容多模态格式发送（base64 data URL）。
  - **错误**：主模型未声明或未配置 `FetchAttachment` 时返回 `ErrImagesUnsupported`（REST 501 `images_unsupported`），提问不保存，不会丢图只按文字回答。读取被拒或内容不符为 `attachment_rejected`，临时错误或单图超时为 `attachment_error`，均可 `RetryMessage`（复用原图片、重新读取）。
  - **回显**：`ConversationMessage.Attachments` 回显用户消息的图片引用。

## 行为变化

- 连接配置 JSON 的每个模型槽位多一个 `"images"` 字段。
- MCP `tools/list` 中 `ask` 的参数多出 `attachments`，`question` 不再是 schema 必填（无图时仍要求）。
- 不带图时，提示词与模型请求体和 v0.9.0 完全相同。
- 带图时同一组图片每轮发给模型两次（意图解析与组织回答），图片 token、上行流量与延迟约翻倍。
- 带图的消息不作为待确认操作的答复、不提出留言；带图提问的回答不进入知识库候选；历史轮次的图片不重发，只记张数。
- 图片内容只在本轮内存中，不写数据库（只存引用）、日志、审计、Gitea 与知识库。

## 数据库

- 新增 `0008_assistant_attachments.sql`：`lingo_assistant_messages` 加列 `attachments jsonb NOT NULL DEFAULT '[]'`（只加列，旧版本照常读写）。
- **须先执行 `lingo.Migrate` 再部署新代码。**

## 回退到 v0.9.0

- `go get github.com/zhouhao4221/lingo@v0.9.0` 后重新部署；`0008` 加的列可以保留，v0.9.0 不读不写它，无需回滚 SQL（v0.9.0 的 `CheckMigrations` 会把 0008 列入 `Unknown`，不影响 `Ready`）。
- 回退前先关闭所有 `images` 声明，并让前端停止提交 `attachments`。
- 回退后已保存的图片引用不再回显。**v0.9.0 不认识图片，以下三点会绕过本版"不丢图只按文字回答"与"带图回答不进知识库候选"的约定**；滚动部署期间 v0.9.0 与 v0.10.0 实例并存时同样存在：
  1. **重试只按文字作答**：v0.9.0 的 `RetryMessage` 不读 `attachments` 列，最近一条带图提问的失败回答仍可重试，会丢掉图片只按文字回答（只发图的提问按空问题处理）。
  2. **评价会产生知识候选**：v0.9.0 的 `RateMessage` 不判断是否带图，把回退前带图 `knowledge_ask` 的回答评为"有帮助"时，问答会经知识库候选进入审核队列，回答文字可能转述了图片中的业务内容。
  3. **新提问的图片被忽略**：v0.9.0 的 REST 与 MCP 会忽略请求中的 `attachments` 字段，带图提问按纯文字处理（只发图时因问题为空被拒）。
- 处置建议：回退或滚动部署期间，提醒用户不要重试或评价带图消息，前端隐藏这类消息的重试与评价按钮；回退后审核知识候选时，找出来源为带图提问的条目并驳回。在接入方应用中 lingo 所在的数据库执行（只读）：

  ```sql
  SELECT k.id, k.status, k.question, a.id AS answer_id, u.id AS question_id
  FROM lingo_knowledge k
  JOIN lingo_assistant_messages a ON a.id = k.source_message_id
  JOIN lingo_assistant_messages u ON u.id = a.reply_to
  WHERE k.source = 'assistant_feedback' AND u.attachments <> '[]'::jsonb;
  ```
